# 本地湖表实验台

一个从零实现的**本地湖表（lakehouse）演示**：数据文件是 Parquet，元数据是 SQLite。
页面可以创建两个写入任务、控制提交顺序、注入崩溃点，查看版本、文件引用与待回收列表，
并用 DuckDB 实时查询每个已提交版本。不依赖任何云存储。

```
Parquet 文件（table/data/…）   ← 版本清单引用的不可变数据文件
SQLite 元数据（var/*.sqlite3） ← 表、版本、文件、提交意图、租约、读者引用、GC/恢复记录
```

## 快速开始

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
./run.sh                      # 打开 http://127.0.0.1:8765
```

测试：

```bash
.venv/bin/python -m pytest tests -q
```

清空演示数据：页面右上角「重置演示数据」，或 `make clean`。

## 提交协议

写入者不会直接改表，而是走一条可恢复的两阶段路径：

1. **取租约**：`leases` 里写下带 TTL 的写入租约（`state=active`），证明这次写入仍然活着。
2. **读版本**：读取当前最新版本 `seq` 作为**基线**。
3. **写临时文件**：Parquet 写到 `_staging/<task>/…`，并在 `files` 里登记为 `staging`。
   （数据文件永远先在私有暂存区出现，不会直接出现在 `data/` 下。）
4. **记录提交意图**：`commit_intents` 写入 `pending`，记录基线版本与文件列表。
   此时任务变成 `prepared`，等待提交。
5. **提交（乐观并发）**：`BEGIN IMMEDIATE` 事务里再次读取最新版本。
   - 若仍是基线版本 → 组装新清单，插入 `versions(seq+1)`，把新文件标 `active`，
     被替换分区里的旧文件标 `superseded`。
   - 若已被别人推进 → 按冲突规则处理（见下），然后重试。
6. **收尾**：任务标 `committed`、租约释放。

版本清单（`versions.manifest_json`）是**不可变**的：每个版本记录该时刻可见的全部文件
及其行数、字节数、sha256。读取某个版本 = 读取它清单里的文件集合，因此并发写入不会
让读者看到半成品。

### 冲突规则

| 情况 | 行为 |
| --- | --- |
| 追加（append），任意分区 | 重试合并到新版本，两边的数据都保留 |
| 分区替换（replace），分区**互不重叠** | 重试合并，各自替换自己的分区 |
| 分区替换（replace），**同一分区被更新过** | **必须重算**：按新版本的分区内容重新派生文件，再提交；绝不直接覆盖 |

重算会写进任务日志（`冲突：seq 1→2 期间分区 ['us'] 被其他写入者更新；按新基线重算，拒绝直接覆盖`），
并把本次任务的 `recomputes` 计数加一，版本统计里也能看到。

## 崩溃点与恢复

页面为每个写入者提供四个崩溃注入点：

| 崩溃点 | 留下的状态 | 恢复行为 |
| --- | --- | --- |
| `after_write` | 临时文件已写，无提交意图 | 任务标记失败；临时文件在回收时清理 |
| `after_intent` | 提交意图 `pending`，无版本 | 意图置 `aborted`，文件标 `orphaned` |
| `after_promote` | 文件已移到正式路径，元数据未提交 | 同 `after_intent`；文件成为孤儿 |
| `after_commit` | 版本已提交，任务未收尾 | 任务对齐为 `committed`，不回滚已提交版本 |

「运行恢复流程」会扫描 `crashed`/`committing` 任务，逐个检查提交意图与版本记录，
再做一次孤儿清扫，并退役崩溃写入者的租约。恢复前后都会跑一致性核对。

> 注：`after_commit` 崩溃点不创建未提交数据，恢复只是补齐任务状态。

## 孤儿回收

「待回收列表」对每个候选文件依次检查三重保护：

1. **提交记录**：文件是否出现在任一**保留中**版本的清单里；
2. **活动写入租约**：是否属于一个仍然有效的写入租约（租约 TTL 未尽，或进程仍在）；
3. **读者引用**：是否被一个仍打开的读者固定（读者打开时可固定某个版本）。

只有三者都不命中的文件才会被删除；已登记文件置 `reclaimed`，磁盘残留但无元数据
记录的文件（`unregistered`）同样被识别并清理。

「保留版本数」填写 N 时只保留最新 N 个版本，旧版本被修剪（`retained=0`），
其独占文件才进入候选。被读者固定的版本不会被修剪。**若回收前一致性核对失败，
回收会直接拒绝执行**，避免破坏诊断证据。

## 一致性核对

「一致性核对」会逐条检查并显示内容指纹：

- SQLite `quick_check`
- 版本序号连续、`parent_id` 链完整
- 每个保留版本的清单文件都存在、大小与 sha256 与文件记录一致
- 清单行数与版本统计一致
- 每个保留版本都能被 DuckDB 实际查询，且查询行数 = 清单行数
- 活跃文件集合 = 最新版本清单的文件集合
- 列出待回收的孤儿文件数（不影响已提交版本）

恢复与回收都会记录「前后核对」结果；每次核对写入 `verifications` 表。

## API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/state` | 版本、任务、意图、文件、租约、读者、事件、待回收列表 |
| POST | `/api/tasks` | 创建写入任务（`op`、`crash_point`） |
| POST | `/api/tasks/{id}/commit` | 提交单个任务 |
| POST | `/api/commits` | 批量提交，`order` 为 `sequential` 或 `concurrent` |
| POST | `/api/recover` | 运行恢复流程 |
| POST | `/api/gc/scan` | 扫描待回收（`retain_versions` 可选） |
| POST | `/api/gc/reclaim` | 执行回收 |
| POST | `/api/verify` | 一致性核对 |
| GET | `/api/query?seq=N` | DuckDB 查询某个版本 |
| GET | `/api/query-all` | 查询全部已提交版本 |
| POST | `/api/readers` | 打开读者引用（可固定版本） |
| POST | `/api/readers/{id}/close` | 释放读者引用 |
| POST | `/api/demo/reset` | 重置演示数据 |

## 代码结构

```
lakehouse/
  data.py       Parquet 读写、确定性的行生成与派生
  db.py         SQLite 模式与事务辅助
  engine.py     提交协议、冲突重算、恢复、GC、一致性核对
  leases.py     写入租约
  readers.py    读者引用
  query.py      DuckDB 查询与内容指纹
  app.py        FastAPI 应用（create_app 便于测试）
  static/       页面（原生 JS，无构建步骤）
tests/          引擎与 HTTP 端到端测试
```

## 演示建议

1. 写入者 A：追加 `us`；写入者 B：替换 `us`（默认分区）。
2. 分别「创建任务」，然后点「先 A 后 B」。B 的日志会出现「冲突…按新基线重算」，
   版本表里 B 的版本带「重算 1」标记。
3. 再试「并发提交（竞态）」：只有一个任务会一次成功，其余自动重试合并或重算。
4. 把 B 的崩溃点设为「崩溃点 ②」，创建任务后提交 → 查看待回收列表里的
   `pending_intent` 保护；运行恢复 → 保护消失，文件变孤儿；执行回收 → 前后核对通过。
5. 在版本行点「固定为读者」，再设置保留版本数并回收，观察 `reader_pin`
   如何阻止旧版本被修剪，释放读者后才能修剪。
